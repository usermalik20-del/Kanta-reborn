# KANTA Android diagnostics: client protocol

The routes are disabled unless the owner explicitly approves and configures private infrastructure. Do not enable Android uploads or ship a live endpoint before approval and privacy-copy review. Manual support remains separate; do not send diagnostic payloads to GitHub.

- **HTTPS `POST /api/diagnostics`**: `Content-Type: application/json` (optional `charset=utf-8`); `Authorization: Bearer <64 lowercase hex characters>` (32 independently generated secure random bytes, encoded as lowercase hex, persisted privately per installation). Body, at most 1,024 UTF-8 bytes: `{"installationId":"01234567-89ab-4def-8123-456789abcdef","active":true,"events":[{"type":"crash","id":"fedcba98-7654-4321-8def-0123456789ab"}]}`. Both IDs are canonical lowercase random UUIDv4; `active` is boolean; `events` is an array of 0–1 objects with exactly `type` (`crash`) and `id` (UUIDv4). Keep the same event UUID on retry. `active:false` must include one crash marker and means crash-only, not opt-out. Use `active:true, events:[]` for an opted-in foreground heartbeat, at most once per UTC day. Extra/duplicate fields, URL query parameters, free text, timestamps and compressed bodies are rejected. The first accepted POST binds the installation ID to its bearer; later POSTs must use the same bearer. `204` is success; activity is deduplicated within the UTC receipt day and crash retries within the 30-day retention window. `429` supplies `Retry-After` in seconds; retry transient transport/5xx errors with bounded backoff only while opted in. `400/401/404/410/413/415` are not automatic upload-retry signals.
- **Android opt-out:** Turn reporting off, cancel transmissions, and erase queued data and local diagnostic identity/secret. Android sends **nothing** after opting out; server data expires automatically. New opt-in uses a fresh independent ID and bearer. A request already received by the server may complete.
- **Optional future explicit removal only: HTTPS `DELETE /api/diagnostics`**. Same content type and bearer, exact body `{"installationId":"01234567-89ab-4def-8123-456789abcdef"}`. `204` for success, including never-seen IDs and same-credential retries; mismatched credential for a known ID returns `404`; subsequent upload for a deleted ID with the matching credential returns `410` during the tombstone lifetime. Not called by the Android opt-out flow. Never reuse a deleted ID.
- No raw body or credential is returned; never put either bearer or installation/event ID in URLs, logs, exports, or backups. A `404` on a disabled route is not a signal to probe another host. Clients must not follow redirects with credentials. Verify Android release config remains off until approved.


## Private database and launch approval

**No launch or provisioning is approved by this change.** Review the privacy notice, retention evidence, hosting-provider terms and the Android opt-in flow; record explicit owner approval for the infrastructure and a separate approval for enabling client uploads. Until then, leave `KANTA_DIAGNOSTICS_ENABLE` unset and the Android endpoint disabled. Preview and local runtime requests are disabled by the production entrypoints, regardless of their other configuration.

1. Use a dedicated private PostgreSQL 16+ database, with verified TLS and network access limited to the approved Vercel deployment and the private maintenance service. No public read role, replication to third parties, shared analytics, GitHub storage, tracing of bodies/authorization, or public database dashboard. Configure backups, WAL/archive and provider logs so diagnostics do not remain recoverable beyond the disclosed limit; opt out of backups/archives for this dedicated database if necessary. Review how Vercel handles edge and provider logs before approval. Never log request bodies, identifiers, secrets, raw addresses, or SQL arguments in KANTA logs.
2. Apply `server/diagnostics.sql` as a dedicated **non-superuser** migration owner (owns schema and the `SECURITY DEFINER` routines). Provision separate runtime and scheduled-maintenance login roles. Neither role should own objects, inherit the migration-owner role, or have direct table privileges or create rights. Restrict database `CONNECT` and default `PUBLIC` privileges, including `TEMP` and public schema `CREATE`, to approved roles. Example grants after creating the named roles privately:

   ```sql
   GRANT USAGE ON SCHEMA kanta_diagnostics TO kanta_diag_runtime, kanta_diag_maintenance;
   GRANT EXECUTE ON FUNCTION kanta_diagnostics.mutate(boolean,text,text,text,boolean,text),
     kanta_diagnostics.metrics() TO kanta_diag_runtime;
   GRANT EXECUTE ON FUNCTION kanta_diagnostics.purge() TO kanta_diag_maintenance;
   ```

3. Install an **independent private scheduler** (not a public route), running `SELECT kanta_diagnostics.purge();` at least every **five minutes**, even if no requests arrive or uploads are disabled. Run it once before first use, alert on a missed run, and have a tested manual fallback within 15 minutes. The app denies writes and aggregate reads if the last successful sweep is older than 12 minutes. A clock outage, maintenance outage or unrestored backup policy can violate physical retention; disable ingestion and handle the incident, rather than relying on stale-maintenance gating to delete data. The SQL removes reports, unneeded identities, and delete tombstones after 29 days, 23 hours and 45 minutes to leave time for the sweep; rate buckets expire after their 15-minute window plus the sweep interval. Identity records remain only while accepted non-duplicate data is recent. Raw IDs, credentials and IPs are not stored: the service writes keyed installation/event/credential digests and short-lived rate keys. Credential removal also deletes the installation's activity and crash rows; only its scoped tombstone remains until expiry to block late retries. Rotation of the HMAC key breaks dedupe/deletion for remaining identities; disable, purge old data and coordinate identity reset before rotating it.
4. In the approved **production** Vercel environment only, configure `KANTA_DIAGNOSTICS_ORIGIN` (single canonical HTTPS origin, no trailing slash), `KANTA_DIAGNOSTICS_DB_URL` (`postgresql://` URL for the runtime role; require percent-encoded credentials as needed, with no query options), and independently generated 64-character lowercase hex `KANTA_DIAGNOSTICS_HMAC_KEY` and `KANTA_DIAGNOSTICS_OWNER_SECRET`. Do not export these to the browser, CI, build tooling, or preview environments. The app also requires Vercel's production environment indicators. Turn on `KANTA_DIAGNOSTICS_ENABLE=true` only after approval. `/owner/diagnostics` (same authorization on `/api/diagnostics-owner`) uses HTTPS Basic authentication: username `owner`, password `KANTA_DIAGNOSTICS_OWNER_SECRET`. Share no accounts or credentials and restrict that route and direct API alias to the owner in the hosting firewall/identity layer where available. Rotate the owner credential on suspected disclosure; browsers may retain Basic credentials until the private browser session closes.
5. Before enabling real clients, verify both routes return 404 without approval; check tiny/oversized streamed requests, trusted source header handling, owner denial and no caching/analytics, database grants and TLS, concurrent shared limits, opt-out with no network, independent cleanup, and provider log/backup settings with synthetic data only. The canonical host must connect directly to Vercel; do not accept an arbitrary reverse proxy or custom forwarding mode. The code trusts only Vercel's `X-Vercel-Forwarded-For` for source addressing and its `X-Forwarded-Proto: https` to recover HTTPS if the Node adapter reconstructs a request as HTTP. Verify Vercel overwrites client attempts to supply those headers on your approved topology and add edge rate limits if needed, including owner-auth attempts, before launch. Deny credential/body logging by the host and any security tooling. To shut down, unset the enable flag and disable the client endpoint; keep database cleanup running until deletion is verified.

## Metrics, limits and local checks

The owner dashboard shows distinct installations reporting activity today and across the last 30 UTC dates, not people or verified devices. Crash counts are separate and deduplicated by installation and marker ID within retention. Downloads are explicitly not tracked here. All windows use server receipt times and are not cumulative. Activity cutoff in the oldest date may be shortened by automatic expiry. Crash-only uploads do not count as active. Anyone who can submit from the public ingest endpoint can generate fresh IDs; these figures are indicative, not proof of genuine devices. The per-installation bearer prevents impersonating established IDs, not fake first-time registrations.

The database enforces shared fixed 15-minute budgets of 300 requests globally, 40 per normalized source (IPv4 or IPv6 /64), 8 per installation and 8 new installations per source. These apply to well-formed mutation attempts; the firewall must absorb large floods before they consume function/database resources. Carrier NAT can group legitimate installations; a distributed flood can exhaust the global budget. This is a deliberately conservative launch cap, not production capacity or app attestation.

Run `npm ci && npm test` in `apps/web` (Node 22). Tests exercise the actual PostgreSQL SQL in an embedded PGlite instance with synthetic data and the Fetch handlers with synthetic requests. An offline Vercel 65.2.0 build can check the two function bundles, dashboard rewrite and that the static output contains public assets but no diagnostics docs, SQL, server code or tests. That is not proof of production routing, trusted headers, TLS, purge scheduling, concurrent database behavior, Android execution or deployed privacy controls. Live enablement, browser/browser-native Basic auth behavior and owner acceptance remain pending.
